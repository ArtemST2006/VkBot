# Данные розыгрыша

## Что хранится сейчас

| Таблица | Назначение | Ключевое ограничение |
| --- | --- | --- |
| `users` | Пользователь VK или MAX, время первого запуска и последнего повторного запуска | `UNIQUE (platform, external_id)` |
| `partners` | Партнёр, его название и ссылка на аккаунт | `slug` уникален |
| `partner_days` | Партнёр конкретной даты, срок и инструкция промокода, название приза, число победителей | `event_date` уникальна |
| `promo_codes` | Загруженный пул кодов и закрепление кода за пользователем | Код уникален в дне; один код на пользователя за день |
| `promo_requests` | Каждое нажатие «Получить промокод», включая повторные запросы и отсутствие кодов | Хранится результат запроса |
| `raffle_entries` | Заявка после успешной проверки подписки и время регистрации | Одна заявка пользователя на партнёрский день |
| `active_days` | Активность от промокода или заявки, которая даёт шанс на главный приз | Один шанс пользователя на партнёрский день |

Дата `partner_days.event_date` — календарный день акции по Москве. Промокод может закончиться, но это не мешает создать заявку в ежедневный розыгрыш.

## Как будут записываться действия

- При запуске бот создаёт пользователя или обновляет `last_seen_at`. Это уже работает.
- Выдача кода должна в одной транзакции найти ранее выданный код либо захватить свободный код (`FOR UPDATE SKIP LOCKED`), закрепить его, записать `promo_requests` и добавить `active_days` через `ON CONFLICT DO NOTHING`. Транзакция и уникальность защитят от двух кодов при одновременных нажатиях.
- После подтверждения подписки сервис должен в одной транзакции создать `raffle_entries` и добавить `active_days`. Повторная проверка вернёт уже существующую заявку.
- «Мои шансы» считает строки `active_days`; сервис показывает не больше 10. Если акция длится больше десяти дней, будущий финальный розыгрыш тоже должен брать максимум десять записей одного пользователя.
- Аналитика считается из времён создания пользователей, `promo_requests`, `promo_codes` и `raffle_entries`; отдельные счётчики пока не нужны.

## Следующие миграции

Перед реализацией розыгрышей понадобятся снимки участников на момент выбора, результаты победителей и резервов, время проведения и подтверждение администратором. Для главного розыгрыша снимок должен содержать отдельный билет на каждый шанс. Перед выдачей призов понадобятся сведения победителя и отдельная запись его согласия на передачу данных. Для уведомлений стоит добавить исходящую очередь с состоянием доставки. Эти таблицы лучше проектировать вместе с соответствующими сценариями: в ТЗ пока не заданы сроки ответа победителя и полный набор призов каждого партнёра.
